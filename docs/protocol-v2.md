# Протокол подписи v2: план (D)

Статус: **только план, кода нет**. Протокол 0.3.11 не меняется: и шлюз, и клиенты продолжают
подписывать v1.

## Зачем

`Content-Type` не входит в каноническую строку v1:

    v1
    client_id
    cert_fingerprint
    epoch
    timestamp
    nonce
    METHOD
    path_or_api_method
    sha256(body)

Поэтому `Content-Type` можно изменить, не сломав подпись. Практические последствия ограничены
(тело всё равно закрыто хешем, а подтверждаемые методы требуют `application/json`), но
расхождение «что подписано» и «как это разберут провайдер и оператор» — это тот класс ошибок,
который лучше закрыть в формате, чем в проверках.

## Новый формат

Каноническая строка v2 добавляет две строки:

    v2
    client_id
    cert_fingerprint
    epoch
    timestamp
    nonce
    METHOD
    path_or_api_method
    sha256(body)
    content_type        (нормализованный media type в нижнем регистре, без параметров)
    content_type_state  ("present" | "absent")

Правила канонизации `Content-Type`:

* Берётся только media type до `;`, обрезаются пробелы, приводится к нижнему регистру:
  `Application/JSON; charset=utf-8` → `application/json`.
* Пустой или отсутствующий заголовок → `content_type = ""`, `content_type_state = "absent"`.
* Значение проверяется тем же регулярным выражением, что и путь (печатаемый ASCII без пробелов),
  иначе `SigningError` — до вычисления HMAC.

`content_type_state` нужен, чтобы «заголовка нет» и «заголовок пустой» не стали одним и тем же
по ошибке клиента.

## Как шлюз различает версии

* Клиент присылает `X-Gatekeeper-Sig: v2`. Заголовка нет → v1 (текущее поведение, обратная
  совместимость).
* Шлюз на переходный период принимает **обе** версии. Версия выбирает только формат
  канонической строки; ключ, epoch, nonce, время и политика — те же.
* `deny_bad_signature` получает `reason="bad_sig_version"`, если версия неизвестна.
* В журнале у `request_intent`/`request_ok` появляется поле `sig_version` (значение `1` или `2`),
  чтобы можно было увидеть, кого ещё не обновили.

Разные версии подписи — **разные** канонические строки, поэтому подпись v1 не пройдёт как v2
и наоборот: даунгрейд-атака «убери заголовок» не проходит, потому что шлюз не пытается
проверить обе версии для одного запроса.

## Порядок обновления

1. Выпустить шлюз, который принимает v1 и v2. Старые клиенты работают без изменений.
2. Обновить клиентов (пакет `blindkey`/`gatekeeper`, `BotApi`, примеры). Клиент v2 шлёт
   `X-Gatekeeper-Sig: v2`.
3. Через один минорный релиз (не раньше) добавить опцию `[server] accept_sig_v1 = false`
   (по умолчанию `true`), затем сменить значение по умолчанию в следующем мажорном/минорном
   релизе с записью в CHANGELOG и SECURITY.md.
4. Удалить v1 из кода только после того, как `sig_version` в журнале не показывает `1`.

Откат: шлюз с поддержкой обеих версий совместим с клиентами обеих версий, поэтому откат
клиента не требует отката шлюза.

## Влияние на существующие механизмы

* `[confirm]`: хеш тела и `Content-Type` уже входят в ключ заявки (`request_key`), поэтому
  подтверждения остаются привязанными к тому же запросу. Меняется только то, что теперь
  `Content-Type` защищён и подписью.
* Повторы и nonce: без изменений.
* `request_intent`/`request_ok`: добавляется поле `sig_version` (аддитивно).
* Клиентские библиотеки: `build_headers` получает параметр `content_type` и `sig_version`;
  по умолчанию — текущее поведение (v1), чтобы примеры не сломались.

## Тесты (обязательные до включения v2)

1. Юнит: канонизация `Content-Type` (регистр, параметры, отсутствие, недопустимые символы).
2. Юнит: v2-подпись с `content_type` не проходит, если заголовок изменён после подписи.
3. Юнит: v1-подпись по-прежнему работает без заголовка версии.
4. Юнит: `X-Gatekeeper-Sig: v2` с подписью v1 → `deny_bad_signature` (без попытки угадать).
5. Юнит: неизвестная версия → `reason="bad_sig_version"`.
6. Интеграция: старый клиент (v1) и новый (v2) одновременно против одного шлюза.
7. Интеграция: подтверждение, созданное клиентом v2, расходуется ровно один раз.
8. Журнал: `sig_version` присутствует в `request_intent` и `request_ok` для обеих версий.
9. Совместимость: `examples/client_send_message.py` работает в обеих версиях.
