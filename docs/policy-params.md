# Параметрические правила политики (дизайн, B4)

Статус: **только дизайн и тесты-спецификация**, кода нет. Ждёт решения владельца проекта.

## Проблема

Политика клиента — это список `METHOD:api` (`allow = ["POST:sendMessage"]`). Метод проверяется,
параметры — нет: клиент с `POST:sendMessage` пишет в любой чат, а `[confirm]` привязывает
подтверждение к хешу тела целиком, поэтому оператор видит параметры, но не ограничен ими.
Ограничение по параметрам — единственный способ выдать агенту «писать только в этот чат».

## Формат правила

    allow = ["POST:sendMessage?chat_id=123,456", "POST:editMessageText?chat_id=-100123"]

* `METHOD:api` — как сейчас, без ограничения параметров (совместимость, но слабее).
* `?` и далее — параметры через `&`; `ключ=значение` или `ключ=значение1,значение2`.
* Значения — литералы, без экранирования и без `%`-декодирования: сравнивается ровно то, что
  в правиле, с тем, что в разобранном JSON.
* Допустимы только плоские скаляры верхнего уровня: строка, число, `true`/`false`. Массив,
  объект или `null` в правиле запрещены (ошибка конфигурации при `add-client`).
* Один параметр в правиле — один раз; повтор ключа — ошибка.

Правило без `?` сохраняет прежнюю семантику: параметры не проверяются. Это осознанно
задокументированное ослабление, а не ошибка: существующие пакеты клиентов не должны ломаться.

## Как проверяется

1. Сначала как сейчас: `Policy.check(method, target)` даёт совпадение по `METHOD:api`.
2. Если у правила есть параметры, тело запроса обязано быть разобрано как JSON строгим
   разбором (`server/confirm_body.py::parse_confirm_params`: без дублей ключей, `NaN`,
   вложенности глубже 64). Для GET тела нет — правило с параметрами на `GET` запрещено
   в конфигурации (у GET параметры были бы в query, а query в подписи — отдельная тема).
3. Каждый параметр правила должен присутствовать в разобранном объекте и совпасть по значению
   (сравнение типов строгое: `123` ≠ `"123"`).
4. Отказ — `deny_policy` с `reason="param_mismatch"` / `"param_missing"` / `"param_not_json"`;
   тело и значения параметров в журнал не пишутся, только имена несовпавших параметров.

Порядок в конвейере: после подписи, nonce и политики, **до** подтверждения. Причина: отказ по
параметрам не должен ни создавать заявку оператору, ни расходовать подтверждение.

## Что это НЕ решает

* `chat_id` в Telegram можно обойти через `@channelusername` или `forwardMessage`; правило
  ограничивает конкретный метод, а не «куда вообще может писать бот». Набор разрешённых
  методов остаётся главным ограничением.
* Вложенные объекты (`reply_markup`, `entities`) не проверяются: правило по ним не выразить.
* Секреты в значениях параметров: правило хранится в `clients.json`, поэтому `chat_id` там
  допустим, а токены — нет (это отдельное правило эксплуатации).

## Совместимость и миграция

* Старые `allow` без `?` работают как раньше, конфиги не ломаются.
* `add-client` принимает новый синтаксис; `list-clients` показывает правила как есть.
* Отозвать и перевыпустить клиента нужно только чтобы **усилить** политику: старый пакет
  с `POST:sendMessage` продолжит работать по своей политике на шлюзе (политика хранится на шлюзе).

## Тесты-спецификация

`tests/unit/test_policy_params_spec.py` — исполняемая спецификация, помеченная `skip`
до реализации. Она фиксирует: разбор правил, семантику совпадения, строгость типов,
порядок относительно подтверждения, коды причин отказа и отсутствие значений в журнале.
