# Дорожная карта

Крупные задачи, которые сознательно не входят в текущие релизы. Здесь же — честная оценка
рисков, чтобы решение «делать/не делать» принималось с открытыми глазами.

## Стриминг ответов upstream

Сейчас ответ upstream буферизуется целиком: `max_response_bytes` на провайдера и общий
`max_total_response_bytes` ограничивают память, при исчерпании потолка запрос получает 502.
Потоковые ответы (`stream: true` у OpenAI, длинные `getUpdates`) не поддерживаются.

Почему это большая задача, а не «просто пробросить байты»:

1. **Память.** Стриминг убирает потолок на один ответ, но появляется новый риск: много
   одновременных потоков. Нужен бюджет на *соединение* (буфер чтения, буфер клиента,
   медленный потребитель), а не на ответ. Медленный клиент с открытым потоком иначе держит
   память и слот провайдера неограниченно долго — нужен таймаут простоя и жёсткий лимит
   «байт в полёте» на соединение.
2. **Фильтр утечек.** Сейчас `filter_response` видит тело целиком: точное значение токена
   ищется по всему ответу, включая границы чанков. При стриминге совпадение может попасть
   на стык чанков, а «отменить уже отправленное» нельзя. Варианты: (а) держать хвост размером
   с самый длинный секрет + окно JSON-разбора и отдавать всё, кроме хвоста (задержка,
   память O(len(secret))); (б) отдавать без проверки на секреты — недопустимо; (в) разрешать
   стриминг только для методов/провайдеров, где токен не может появиться в ответе, — требует
   отдельного списка и ревью на каждого провайдера.
3. **NDJSON и SSE.** Фильтр сейчас режет NDJSON по `\n`; для SSE нужны границы событий,
   а для OpenAI — ещё и разбор каждого события. Ошибка в разборе не должна рвать соединение
   молча: клиент должен увидеть терминальное событие ошибки.
4. **Журнал.** Запись `request_ok` появляется после ответа. При стриминге ответ «уже начался»,
   поэтому нужен отдельный итог: `request_stream_started` / `request_stream_finished`
   с числом байт и причиной обрыва. Иначе журнал снова покажет намерение без итога (см. A1).
5. **Таймауты и отмена.** Обрыв клиента должен освобождать слот провайдера и бюджет памяти;
   обрыв upstream после начала стрима — это «частично выполнено», а не «не выполнено».
6. **Метрики.** Нужны `gk_stream_seconds`, `gk_stream_bytes`, `gk_stream_aborted_total`
   с причиной, иначе инциденты не видны.

Оценка: это отдельный минорный релиз с собственным аудитом фильтра утечек и нагрузочным
тестом на медленных клиентов. Делать после того, как появится реальный сценарий (например,
потоковые ответы LLM через шлюз), и только с тестами на стык чанков и на отмену.
