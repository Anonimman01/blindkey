# Модель угроз

Документ описывает, от чего шлюз защищает, на что рассчитывает и где защиты нет.
Статус кода: MVP (шаги 1-6 и пункты 1-5 плана) и внешние якоря журнала (`audit-anchor`);
автозаморозка, подтверждения, ротация ключей и другие провайдеры относятся к v2.

## Активы

1. Токен бота (полный контроль над ботом).
2. Клиентские данные: сертификат, `client.key`, `master.secret`.
3. Журнал (доказательная база инцидента).
4. Доступность шлюза.

## Границы доверия

    Клиент (ненадёжная среда) ══ mTLS 1.3 + HMAC ══▶ Шлюз (доверенный) ──HTTPS──▶ Telegram
                                                         │
                                          офлайн: ca.key (вне шлюза)

Доверенными считаются: машина шлюза, офлайн-хранилище `ca.key`, администратор.
Недоверенными: клиентская машина, сеть между клиентом и шлюзом, любой посторонний с доступа к порту.

## Противники и меры

| Угроза | Мера | Остаточный риск |
|---|---|---|
| Утечка клиентских данных (cert + key + master.secret) | белый список, лимиты и бюджеты, `revoke` / `freeze` без перезапуска, запись в журнал | до отзыва вор действует в рамках прав клиента |
| Утечка только части данных (только ключ подписи или только сертификат) | отпечаток сертификата входит в подпись; TLS требует сертификат | нужны обе части |
| Посторонний с открытым портом | mTLS, pin на CA, лимит соединений, бан по IP, нейтральные ответы | перегрузка на уровне сети (нужен файрвол) |
| Перехват и повтор запроса | окно времени 30 с, nonce-кэш, TLS 1.3 | кэш в памяти: после перезапуска окно повтора до 60 с |
| Подделка пути (SSRF, обход белого списка) | строгая проверка символов, точное сравнение, путь upstream берётся из правила | зависит от корректности `policy.py` |
| Request smuggling, slowloris, огромные заголовки | h11 + собственные лимиты и общие сроки, один запрос на соединение | см. тесты `tests/unit/test_http_io.py`, `tests/integration/test_network_abuse.py` |
| Утечка токена в ответе upstream | фильтр ответа (блок по точным секретам и полному шаблону токена) | нестандартное кодирование токена в ответе |
| Токен в логах и ошибках | `redact` в журнале, нейтральные ответы клиенту | новые места логирования нужно проверять вручную |
| Правка или удаление записей журнала | цепочка хешей, `audit-verify`, `chain.head`; внешние якоря (`audit-anchor`, `audit-verify --anchors`) | без якорей: удаление хвоста вместе с `chain.head` и полная перезапись; с якорями не видны только записи, сделанные после последнего якоря, и якоря, лежащие на самом шлюзе |
| Кража клиентских файлов, о которой никто не знает | приманки: любой запрос с поддельным сертификатом даёт `decoy_triggered` и бан | приманка не ловит вора, который знает, что она приманка |
| Компрометация шлюза | изоляция машины, systemd-ограничения, права 0600/0700, `ca.key` не на шлюзе | токен раскрыт; перевыпуск в @BotFather, новый CA |
| Компрометация ca.key | хранится офлайн | выпуск произвольных клиентов; нужен новый CA и перевыпуск всех пакетов |

## Явно вне модели

- Атаки на Telegram и на TLS как протокол.
- Вредоносный администратор шлюза.
- Физический доступ к машине шлюза.
- Содержимое сообщений: шлюз и Telegram видят его в открытом виде.
- Отказ в обслуживании на сетевом уровне.

## Допущения

- Часы шлюза и клиентов синхронизированы (NTP) в пределах 30 с.
- Один шлюз на один каталог данных (замок журнала рекомендательный, на NFS не гарантирован).
- Бан приманки действует на IP целиком, включая настоящих клиентов с того же адреса.
- Неудачные TLS-рукопожатия пишутся в журнал (`DENY_TLS_HANDSHAKE`) с ограничением частоты по IP:
  до 5 записей подряд, затем 1 в секунду. При шторме подключений в журнале есть не все попытки.
