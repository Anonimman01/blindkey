# Модель угроз

Документ описывает, от чего шлюз защищает, на что рассчитывает и где защиты нет.
Версия 0.3.8. Статус кода: MVP (шаги 1-6 и пункты 1-5 плана), внешние якоря журнала (`audit-anchor`) и автозаморозка
по аномалиям (опция `[anomaly]`, по умолчанию выключена), подтверждение опасных действий (опция
`[confirm]`, по умолчанию выключена); ротация ключей относится к v2; провайдеры Telegram, GitHub, OpenAI, Vercel и Cloudflare реализованы (несколько провайдеров на одном шлюзе с 0.3.5: клиент привязан к одному провайдеру, все секреты в памяти одного процесса).

## Активы

1. Токен upstream: бота Telegram или доступа к GitHub, OpenAI, Vercel или Cloudflare (полный контроль над ботом или аккаунтом в рамках токена; у OpenAI ещё и расход).
2. Клиентские данные: сертификат, `client.key`, `master.secret`.
3. Журнал (доказательная база инцидента).
4. Доступность шлюза.

## Границы доверия

    Клиент (ненадёжная среда) ══ mTLS 1.3 + HMAC ══▶ Шлюз (доверенный) ──HTTPS──▶ Telegram / GitHub / OpenAI / ...
                                                         │
                                          офлайн: ca.key (вне шлюза)

Доверенными считаются: машина шлюза, офлайн-хранилище `ca.key`, администратор.
Недоверенными: клиентская машина, сеть между клиентом и шлюзом, любой посторонний с доступа к порту.

## Противники и меры

| Угроза | Мера | Остаточный риск |
|---|---|---|
| Утечка клиентских данных (cert + key + master.secret) | белый список, лимиты и бюджеты, `revoke` / `freeze` без перезапуска, автозаморозка при серии отказов (`[anomaly]`), запись в журнал | до отзыва вор действует в рамках прав клиента; вор, который не делает ошибок (подпись верна, метод разрешён), автозаморозку не вызывает |
| Вор клиентских данных вызывает опасный метод (удаление, бан) | `[confirm]`: метод выполняется только после `gatekeeper approve` на шлюзе, подтверждение одноразовое, с ограниченным сроком и привязано к хешу тела; тело разбирается как строгий JSON (без дублей ключей), оператор видит разобранные параметры; квота проверяется до подтверждения, поэтому отказ по бюджету его не расходует | оператор одобряет не глядя; вор может завалить очередь заявок (лимит 20 на клиента) и отвлечь оператора; методы вне `[confirm]` не защищены; `form` и `multipart` для таких методов не подходят; параметры политикой не ограничиваются |
| Утечка только части данных (только ключ подписи или только сертификат) | отпечаток сертификата входит в подпись; TLS требует сертификат | нужны обе части |
| Посторонний с открытым портом | mTLS, pin на CA, лимит соединений, бан по IP, нейтральные ответы | перегрузка на уровне сети (нужен файрвол) |
| Перехват и повтор запроса | окно времени 30 с, nonce-кэш, TLS 1.3 | nonce хранятся в `state.db`; при потере питания последние транзакции могут пропасть, окно повтора не больше 60 с |
| Флуд подписанных запросов, заполняющий nonce-кэш | лимит nonce на клиента (один клиент не занимает весь кэш), при переполнении новые nonce отклоняются, а не вытесняются | клиент с действующим ключом может отказывать в обслуживании самому себе до истечения TTL nonce (около 70 с); защита от повтора при этом не ослабевает |
| Подделка пути (SSRF, обход белого списка) | строгая проверка символов, точное сравнение, путь upstream берётся из правила | зависит от корректности `policy.py` |
| Request smuggling, slowloris, огромные заголовки | h11 + собственные лимиты и общие сроки, один запрос на соединение | см. тесты `tests/unit/test_http_io.py`, `tests/integration/test_network_abuse.py` |
| Утечка токена в ответе upstream | фильтр ответа (блок по точным значениям секрета, в том числе в JSON-экранированном виде) | нестандартное кодирование токена в ответе; чужие токеноподобные строки намеренно не блокируются |
| Токен в логах и ошибках | `redact` в журнале, нейтральные ответы клиенту | новые места логирования нужно проверять вручную |
| Правка или удаление записей журнала | цепочка хешей, `audit-verify`, `chain.head`; внешние якоря (`audit-anchor`, `audit-verify --anchors`) | без якорей: удаление хвоста вместе с `chain.head` и полная перезапись; с якорями не видны только записи, сделанные после последнего якоря, и якоря, лежащие на самом шлюзе; ротация (`audit_max_bytes`, `audit_keep`) удаляет самые старые сегменты, поэтому нужны внешние копии архивов и якоря |
| Рост журнала и обрыв записи (полный диск, `kill -9`, потеря питания) | ротация по размеру; ограничение записей об отказах; автоусечение недописанной последней строки с событием `audit_tail_repaired` (число и SHA-256 удалённых байт) и `gatekeeper audit-repair` | оборванная запись исчезает из журнала (клиенту она не подтверждалась); другие повреждения блокируют запуск; при полном диске запросы получают 500, пока не освободится место |
| Сбой журнала посреди запроса | запись `request_intent` до обращения к провайдеру: при недоступном журнале действие не выполняется | запись результата идёт после upstream: при сбое в этот момент клиент получает 500, действие уже выполнено, в журнале только намерение; не идемпотентные запросы вслепую повторять нельзя |
| Кража клиентских файлов, о которой никто не знает | приманки: любой запрос с поддельным сертификатом даёт `decoy_triggered` и бан | приманка не ловит вора, который знает, что она приманка |
| Утечка `clients.json` (там `master_secret` открытым текстом) | права 0600 и владелец службы проверяются при старте шлюза и в `gatekeeper status`; запись с fsync каталога | файл из бэкапа или копия без сохранения прав: проверка поймает только при следующем старте; шифрование файла не предусмотрено |
| Компрометация шлюза | изоляция машины, systemd-ограничения, права 0600/0700, `ca.key` не на шлюзе | токен раскрыт; перевыпуск токена у провайдера (@BotFather, настройки GitHub, OpenAI, Vercel, Cloudflare), новый CA |
| Компрометация ca.key | хранится офлайн; можно зашифровать фразой (`--ca-key-pass-file`, `GATEKEEPER_CA_KEY_PASSPHRASE`) | выпуск произвольных клиентов; нужен новый CA и перевыпуск всех пакетов; ключ по умолчанию без пароля, а фраза в файле или окружении рядом с ним защищает слабее, чем отдельное хранение |
| Истечение серверного сертификата (365 дней) | `gatekeeper renew-server`; `gatekeeper status` предупреждает за 30 дней | предупреждение видно только при запуске `status`, мониторинга срока нет; после истечения клиенты не подключаются |
| Исчерпание памяти большими ответами upstream | `max_response_bytes` и `max_inflight` на провайдера, общий `max_total_response_bytes`; при исчерпании 502 | ответ буферизуется целиком, стриминг не поддерживается; общий потолок по умолчанию 256 МиБ |

## Явно вне модели

- Атаки на Telegram, GitHub, OpenAI, Vercel, Cloudflare и на TLS как протокол.
- Расход средств у провайдера: суточный бюджет считает запросы, а не деньги и токены OpenAI.
- Вредоносный администратор шлюза.
- Физический доступ к машине шлюза.
- Содержимое сообщений: шлюз и Telegram видят его в открытом виде.
- Отказ в обслуживании на сетевом уровне.

## Допущения

- Часы шлюза и клиентов синхронизированы (NTP) в пределах 30 с.
- Один шлюз на один каталог данных (замок журнала рекомендательный, на NFS не гарантирован).
- Бан приманки действует на IP целиком, включая настоящих клиентов с того же адреса.
- Журнал с оборванной последней строкой (сбой питания или `kill -9` посреди записи) шлюз с 0.3.8
  чинит сам, отрезая хвост по последнему `\n` и записывая `audit_tail_repaired`. Это допустимо,
  потому что оборванная запись клиенту не подтверждалась, а след правки остаётся в журнале.
  Журнал без единой полной строки и любые другие повреждения по-прежнему блокируют запуск.
- Освободить место на диске при полном диске должен оператор: шлюз отвечает 500, пока запись в
  журнал невозможна (fail closed).
- Серверный сертификат продлевается вручную (`renew-server`) до истечения срока.
- Шлюз и файл подтверждений работают под одним пользователем: компрометация процесса шлюза
  позволяет самому выписать подтверждение (вредоносный администратор вне модели).
- Неудачные TLS-рукопожатия пишутся в журнал (`DENY_TLS_HANDSHAKE`) с ограничением частоты по IP:
  до 5 записей подряд, затем 1 в секунду. При шторме подключений в журнале есть не все попытки.
