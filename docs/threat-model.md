# Модель угроз

Документ описывает, от чего шлюз защищает, на что рассчитывает и где защиты нет.
Версия 0.3.3. Статус кода: MVP (шаги 1-6 и пункты 1-5 плана), внешние якоря журнала (`audit-anchor`) и автозаморозка
по аномалиям (опция `[anomaly]`, по умолчанию выключена), подтверждение опасных действий (опция
`[confirm]`, по умолчанию выключена); ротация ключей относится к v2; провайдеры Telegram и GitHub реализованы (один провайдер на экземпляр шлюза, несколько в одном экземпляре относятся к v2).

## Активы

1. Токен upstream: бота Telegram или доступа к GitHub (полный контроль над ботом или аккаунтом в рамках токена).
2. Клиентские данные: сертификат, `client.key`, `master.secret`.
3. Журнал (доказательная база инцидента).
4. Доступность шлюза.

## Границы доверия

    Клиент (ненадёжная среда) ══ mTLS 1.3 + HMAC ══▶ Шлюз (доверенный) ──HTTPS──▶ Telegram / GitHub
                                                         │
                                          офлайн: ca.key (вне шлюза)

Доверенными считаются: машина шлюза, офлайн-хранилище `ca.key`, администратор.
Недоверенными: клиентская машина, сеть между клиентом и шлюзом, любой посторонний с доступа к порту.

## Противники и меры

| Угроза | Мера | Остаточный риск |
|---|---|---|
| Утечка клиентских данных (cert + key + master.secret) | белый список, лимиты и бюджеты, `revoke` / `freeze` без перезапуска, автозаморозка при серии отказов (`[anomaly]`), запись в журнал | до отзыва вор действует в рамках прав клиента; вор, который не делает ошибок (подпись верна, метод разрешён), автозаморозку не вызывает |
| Вор клиентских данных вызывает опасный метод (удаление, бан) | `[confirm]`: метод выполняется только после `gatekeeper approve` на шлюзе, подтверждение одноразовое, с ограниченным сроком и привязано к хешу тела | оператор одобряет не глядя; вор может завалить очередь заявок (лимит 20 на клиента) и отвлечь оператора; методы вне `[confirm]` не защищены |
| Утечка только части данных (только ключ подписи или только сертификат) | отпечаток сертификата входит в подпись; TLS требует сертификат | нужны обе части |
| Посторонний с открытым портом | mTLS, pin на CA, лимит соединений, бан по IP, нейтральные ответы | перегрузка на уровне сети (нужен файрвол) |
| Перехват и повтор запроса | окно времени 30 с, nonce-кэш, TLS 1.3 | nonce хранятся в `state.db`; при потере питания последние транзакции могут пропасть, окно повтора не больше 60 с |
| Флуд подписанных запросов, заполняющий nonce-кэш | лимит nonce на клиента (один клиент не занимает весь кэш), при переполнении новые nonce отклоняются, а не вытесняются | клиент с действующим ключом может отказывать в обслуживании самому себе до истечения TTL nonce (около 70 с); защита от повтора при этом не ослабевает |
| Подделка пути (SSRF, обход белого списка) | строгая проверка символов, точное сравнение, путь upstream берётся из правила | зависит от корректности `policy.py` |
| Request smuggling, slowloris, огромные заголовки | h11 + собственные лимиты и общие сроки, один запрос на соединение | см. тесты `tests/unit/test_http_io.py`, `tests/integration/test_network_abuse.py` |
| Утечка токена в ответе upstream | фильтр ответа (блок по точным значениям секрета, в том числе в JSON-экранированном виде) | нестандартное кодирование токена в ответе; чужие токеноподобные строки намеренно не блокируются |
| Токен в логах и ошибках | `redact` в журнале, нейтральные ответы клиенту | новые места логирования нужно проверять вручную |
| Правка или удаление записей журнала | цепочка хешей, `audit-verify`, `chain.head`; внешние якоря (`audit-anchor`, `audit-verify --anchors`) | без якорей: удаление хвоста вместе с `chain.head` и полная перезапись; с якорями не видны только записи, сделанные после последнего якоря, и якоря, лежащие на самом шлюзе |
| Кража клиентских файлов, о которой никто не знает | приманки: любой запрос с поддельным сертификатом даёт `decoy_triggered` и бан | приманка не ловит вора, который знает, что она приманка |
| Утечка `clients.json` (там `master_secret` открытым текстом) | права 0600 и владелец службы проверяются при старте шлюза и в `gatekeeper status`; запись с fsync каталога | файл из бэкапа или копия без сохранения прав: проверка поймает только при следующем старте; шифрование файла не предусмотрено |
| Компрометация шлюза | изоляция машины, systemd-ограничения, права 0600/0700, `ca.key` не на шлюзе | токен раскрыт; перевыпуск токена у провайдера (@BotFather, GitHub), новый CA |
| Компрометация ca.key | хранится офлайн | выпуск произвольных клиентов; нужен новый CA и перевыпуск всех пакетов |

## Явно вне модели

- Атаки на Telegram, GitHub и на TLS как протокол.
- Вредоносный администратор шлюза.
- Физический доступ к машине шлюза.
- Содержимое сообщений: шлюз и Telegram видят его в открытом виде.
- Отказ в обслуживании на сетевом уровне.

## Допущения

- Часы шлюза и клиентов синхронизированы (NTP) в пределах 30 с.
- Один шлюз на один каталог данных (замок журнала рекомендательный, на NFS не гарантирован).
- Бан приманки действует на IP целиком, включая настоящих клиентов с того же адреса.
- Журнал с оборванной последней строкой (сбой питания или `kill -9` посреди записи) шлюз считает
  повреждённым и не запускается, пока оператор не усечёт хвост (README, раздел «Журнал»). Это
  отказ в обслуживании при сбое, но не обход защиты.
- Шлюз и файл подтверждений работают под одним пользователем: компрометация процесса шлюза
  позволяет самому выписать подтверждение (вредоносный администратор вне модели).
- Неудачные TLS-рукопожатия пишутся в журнал (`DENY_TLS_HANDSHAKE`) с ограничением частоты по IP:
  до 5 записей подряд, затем 1 в секунду. При шторме подключений в журнале есть не все попытки.
