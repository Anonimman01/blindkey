# Безопасность

## Сообщить об уязвимости

Не открывайте публичный issue. Сообщите приватно через GitHub: вкладка
Security -> Report a vulnerability в репозитории (private vulnerability reporting).
Приложите шаги воспроизведения и версию.

## Что защищает шлюз

- Токен бота лежит только на шлюзе; клиенты получают отзываемые сертификаты.
- mTLS (только TLS 1.3, клиентский сертификат обязателен, pin на CA) и HMAC-подпись каждого запроса.
- Белый список «метод + путь» на клиента; путь к upstream берётся из правила, не от клиента.
- Журнал с цепочкой хешей, приманки, лимиты, фильтр ответов upstream.

## Что НЕ защищено (честно)

- Взлом самого шлюза раскрывает токен бота. Нужна отдельная машина, непривилегированный
  пользователь, systemd-ограничения (`deploy/gatekeeper.service`), файрвол.
- Клиент и шлюз на одной машине: защита теряет смысл.
- Telegram и шлюз видят содержимое сообщений.
- До отзыва украденные клиентские данные работают в рамках белого списка и лимитов.
- Токен, который хоть раз лежал в обход шлюза, нужно перевыпустить в @BotFather.
- Журнал без внешних якорей не защищает от полной перезаписи. Якоря (`audit-anchor`) нужно
  хранить вне шлюза и создавать регулярно; записи после последнего якоря ими не прикрыты.
- Лимиты, nonce и баны живут в памяти и сбрасываются при перезапуске.
- Проект не проходил независимый аудит.

Подробнее: `docs/threat-model.md`.
